Your agent can build a whole feature while you make a coffee. So what are you there for? Matt Pocock has an answer. He teaches developers for a living, he made Total TypeScript, and his answer is a folder of agent skills with more stars on GitHub than React. On October fourth he shipped version one point three. Say you run a coffee subscription app, and you type: let users pause their subscription. Ten minutes later there's a Pause button, the tests pass, and it works. Then a customer pauses on the twenty-ninth and still gets a bag of coffee on the first, because it was already roasted and packed. Somebody had to decide what happens to that bag. Your agent decided. It also decided whether the bill stops today or at the end of the month, how long a pause can last and what the reminder email says. You wrote one sentence, so it filled every gap with a guess and kept going. Agents are polite like that. Couldn't you write a longer prompt? You'd only write down the decisions you thought of, and the packed bag wasn't one of them. Matt turns the conversation around. Before any code exists, the agent interviews you, and his skill for it is called grill me: a relentless interview about your plan. Picture the feature as a tree of decisions in the fog. Pause sits at the top. Under it hang billing, the packed bag and how long a pause lasts, and each of those has more decisions hanging off it. The grilling skill maps that tree, finds every decision whose parent is already settled, called the frontier, and asks you all of them in one numbered round. Each question comes with the agent's recommended answer, so a lot of the time you type "yes, yes, no, end of the month". Your answers settle a layer, a new frontier lights up, and the fog moves back. Facts are the agent's job: if the answer is somewhere in the code, it sends a helper agent to go and read it. Decisions are yours. And it can't start on the code until the frontier is empty and you agree you're on the same page. On a small change Matt gets about six questions, and around twenty on a normal one. While filming a lesson for his course, it once asked him forty-six. His post about it: dude, chill, you're scaring the noobs. Halfway through, you mention customers can skip a month. The agent stops you: is skip the same thing as pause? This version is called grill with docs, and it keeps a glossary in your repo while it grills. Pause gets one line: no deliveries and no charges until the resume date. Skip gets another: one delivery missed, billing carries on. Under each, the words to avoid, like hold and freeze. An agent dropped into a project has to guess its jargon, so it uses twenty words where one would do. Matt once read out a real reply from Opus 5 that ended, "It is genuinely load bearing though, so that's how you know it matters." Then he asked the obvious question. What does that mean? So there's a skill for that moment too. Type wait what, and the agent pitches its last message again in plain English, using the words from your glossary. Some questions won't settle by talking, like what the pause screen should look like. For those ungrillable ones, the agent hands off to a fresh session, builds a throwaway prototype with a few screens that look nothing alike, and you click through them and pick. Then the answer comes back to the grilling. When the fog is gone, you stay in the same chat and type to spec. No more questions this time. The agent writes up everything you settled: the problem, the fix, and a long numbered list of user stories. As a customer who pauses after my bag is packed, I still get that bag, and my pause starts after it. First, though, it agrees the seams with you, the places where the tests will poke at the feature, and the ideal number of seams is one. For us that's the billing module. The spec goes up as an issue in your tracker, labelled ready for agent. The spec is the destination. The tickets are the journey. Why tickets? Because an agent gets worse the more it's holding. Somewhere past a hundred fifty thousand tokens it stops reasoning as sharply, and the part before that is the smart zone, a term Matt says he stole from Dex Horthy. So to tickets cuts the spec into slices that each fit one fresh session. Each slice runs through every layer, database to button, so it works on its own. Ticket one: pausing stops the next charge. Ticket two: a resume date. Ticket three: the packed bag. Ticket four: the emails. Three and four can't start until one is done. The rule of thumb: guess the tokens a job needs and divide by a hundred fifty thousand, so a million-token refactor becomes seven tickets. Then the build. Type implement on ticket one, clear the chat, implement ticket two, so every ticket starts in a clean head. Or use implement spec, new in one point three, which builds the whole spec in one go: one agent per ready ticket, each in its own copy of the repo, all landing on one branch. Either way it works test first. A failing test at the agreed seam, then only enough code to pass it, one slice at a time. The skill used to have a refactoring step too. Matt dropped it, because the agent "never, ever, ever did it". Refactoring moved to review, and review happens at a different desk. An agent that has written some code thinks it's fine, because it wrote it. So code review hands the diff to two fresh agents. One reads it against the spec, looking for anything missing, anything nobody asked for and anything that looks done but is wrong. The other reads it against your coding standards and a dozen classic code smells from Martin Fowler's Refactoring. The agent that wrote the code never saw those standards. Models are bad at following a list of don'ts while they build, and a reviewer hunting for exactly those problems has nothing else on its mind. On ticket three, the spec reviewer quotes our user story back: pausing today cancels the packed bag. When the fix goes up as a pull request, a skill called PR writes the description. It's adapted from Dex Horthy's show me skill: the smallest picture that explains the change, proof from before and after, and a section called merge danger. Is this a one-way door or a two-way door, and how big is the blast radius? Ours adds a column to the subscriptions table. Two-way door, blast radius billing. The last step is the other big one in one point three. Before you clear the chat, type retro. The agent reads back through the session it just had and suggests changes to its surroundings: the repo, the checks, the instructions. That matters, because your agent won't complain. It bumps into problems, keeps pushing until the feature works, and the struggle stays buried in the transcript. Here it spent ten minutes hunting for the billing code, so it suggests one line in your agent instructions that points at it. It called the payment provider directly twice, which your codebase never does, so that becomes a lint rule. A mistake a machine can spot gets a check, full stop, and the written coding standards keep only the judgment calls. Found an error? Do a retro, and make it impossible next time. People keep asking Matt to put retro on autopilot, and he says don't, because an agent fixing its own findings ends up chasing false positives. It only suggests, and you pick which fixes to keep.
